## 五、開發前審查中待確認事項的處理決策

以下為你此次審查報告所提出的技術問題之處理原則。除特別標記者外，授權你採用下列方案進行第一版實作，後續可依實際測試結果調整。

### 5.1 圖片容量及圖片處理

採用以下規格：

- 單張原始上傳圖片上限為 2,000,000 bytes。
- 支援 PNG、JPG、JPEG、WebP。
- 圖片最長邊自動縮小至 1024 px。
- 保持原始圖片比例。
- 小於 1024 px 的圖片不額外放大。
- 提供圖片裁切及預覽功能。
- 提供完整顯示與填滿裁切兩種模式。
- 使用正規化裁切座標或其他合理的方式保存裁切資訊。
- 不得因圖片比例不同而使藥品模型尺寸改變。

圖片壓縮格式及品質參數交由你實作、測試並選擇合理設定。

應兼顧圖片辨識度、記憶體使用量與 HTML 成果檔案大小。

若無上傳圖片，則使用白色包裝模型，並自動印上英文學名及劑量。長文字須自動換行或縮小字級，避免超出模型表面。

### 5.2 藥品重複判斷

維持三欄共同判定：

- 英文學名 genericName
- 劑量 strength
- 劑型 dosageFormId

英文學名正規化方式：

`genericName.trim().toLowerCase()`

劑量正規化方式：

`strength.replace(/\s/gu, "").toLowerCase()`

劑型以固定 ID 比較。

補充規則：

- 保留英文學名內部空白的差異。
- 不自動合併學名同義詞。
- 不拆分複方成分。
- 不進行劑量等價單位換算。
- 500 MG 與 500mg 視為相同。
- 0.5 g 與 500 mg 視為不同。
- 保留原始輸入文字供介面顯示。
- 同批教材中若有重複品項，依清單順序保留第一筆有效項目。
- 主題進貨遇到既有重複品項時，自動跳過，不更新原品項。
- 編輯藥品時，重複檢查應排除該品項自身 ID。

新增、編輯、主題進貨、教材發布驗證應共用同一套驗證邏輯。

### 5.3 藥架名稱

維持選填、可同名、最多 20 字元的規則。

採用使用者實際看見的字元作為計數基準，合成 Unicode 字元應合理處理。

可優先使用 Intl.Segmenter 或其他可靠的實作方式，並提供必要的相容處理。

不同藥架即使名稱相同，仍須透過固定位置編號辨識。

### 5.4 圖片及 3D 資源清理

接受你的圖片資源管理提案。

請在適當時機釋放：

- 不再使用的 Blob URL。
- Three.js Texture。
- 不再使用的 Geometry。
- 不再使用的 Material。
- 已卸載場景及相關 GPU 資源。
- 不再需要的事件監聽器及非同步請求。

共享模型、共享材質及共享貼圖不得因單一物件刪除而被錯誤釋放。

重新開始遊戲時，須確實清除本次體驗的資料與資源，並取消或隔離尚未完成的非同步進貨請求，避免舊資料回流。

管理端圖片的實體刪除必須先檢查全部草稿及已發布版本的引用。

若無法安全確認圖片已不再使用，第一版可暫時保留該圖片，不必實作高風險的自動清除功能。

### 5.5 舊教材相容性

目前以全新專案進行開發。

若尚無既有正式教材，不需要額外建立複雜的舊版資料遷移功能。

但資料結構應具有明確的 schemaVersion 或等效版本識別機制。

未來若需匯入舊教材，遇到缺少必填欄位、非法劑型或不相容資料時，應提供明確錯誤訊息，不得自行捏造藥品資料。

## 六、必須維持的核心功能

### 6.1 遊戲定位與生命週期

My Pharmacy 是以藥學教育、短暫體驗及成果展示為目的的互動式 3D 網頁遊戲。

必須符合：

- 不需要學生登入。
- 初始藥品種類為零。
- 初始具有 OTC-01、OTC-02 兩座空藥架。
- 初始無任何已上架藥品。
- 同一次遊戲期間，內部頁面切換保留資料。
- 重新整理網頁後恢復初始狀態。
- 關閉頁面後不永久保存個人進度。
- 不提供離頁提醒。
- 不提供個人 JSON 備份、匯入、還原或合併。
- 不提供已分享成果的續編功能。
- 僅於 3D 藥局總覽提供重新開始遊戲按鈕。
- 重新開始前須二次確認。

已下載的 HTML 成果及已發布的管理端教材不受重新開始功能影響。

### 6.2 首頁及基本操作介面

正式名稱：

我的藥局 My Pharmacy

首頁採用白色與醫療綠為主要美術風格。

封面為原創、簡化的 3D 社區藥局外觀。

首頁僅提供兩個主要操作入口：

1. 我要管理藥品。
2. 進入我的藥局。

「我要管理藥品」提供：

1. 從已知的代碼進貨。
2. 我要進貨。
3. 管理藥品清單。

請勿任意新增會改變主要使用者流程的功能。

### 6.3 藥品資料管理

僅以下三項為必填：

- 英文學名。
- 劑量。
- 劑型。

其餘選填欄位直接顯示，不使用預設收合的方式：

- 商品名。
- 藥理分類。
- 適應症。
- OTC／RX 分類。
- 3D 包裝模板。
- 正面包裝圖片。

藥理分類及劑量皆使用自由文字。

劑型使用 v22 已確認的 27 種固定中英文並列選項，維持正式清單順序及已確認的預設包裝映射。

不得自行新增、刪除或合併劑型。

藥品清單提供英文學名及商品名搜尋，採用不區分大小寫的部分文字比對。

建議獨立藥架場景的選藥清單共用相同搜尋元件。

刪除個人藥品目錄品項時，須二次確認，並同時移除全藥局中所有引用該品項的擺放紀錄。

### 6.4 固定 3D 包裝模型

所有藥品使用下列三種標準包裝模板：

- 藥盒：寬 9 × 高 15 × 深 5 cm。
- 藥瓶：直徑 8 cm、高 12 cm。
- 藥袋：寬 10 × 高 14 × 深 2 cm。

**管理端及使用者端均不得提供任何個別藥品模型尺寸調整功能。**

不得提供：

- 長寬高輸入欄位。
- 模型尺寸調整滑桿。
- 個別藥品縮放比例設定。
- 因圖片尺寸不同而自動改變模型尺寸的功能。

允許使用者選擇三種包裝模板、裁切圖片、調整貼圖及縮放觀看視角。

未指定模板時，依已確認的 27 種劑型映射自動選擇。

### 6.5 OTC／RX 分類提醒

未填寫 OTC／RX 分類時，顯示為未分類，不自行推論藥品分類。

- OTC 放入 OTC 區：允許。
- OTC 放入 RX 區：允許。
- RX 放入 RX 區：允許。
- RX 放入 OTC 區：允許，顯示 5 秒警告。
- 未分類放入任一區：允許，顯示 3 秒提示。

提示不阻擋操作，不形成永久警告標記。

放置及替換藥品皆適用相同規則。

### 6.6 藥架管理

全藥局最多七座藥架，最少維持一座。

- OTC 固定位置五個。
- RX 固定位置兩個。
- 各區可為零座，但全藥局至少一座。
- 每個固定位置最多建立一座藥架。
- 尚未建立藥架的位置顯示地面加號。
- 不允許任意拖移藥架位置。
- OTC 為開放式金屬藥架。
- RX 為白色金屬藥架，具有背板。

每座藥架：

- 寬 120 cm。
- 高 180 cm。
- 深 40 cm。
- 層板厚 2 cm。
- RX 背板厚 1 cm。
- 四層格位依序為 2、3、3、2。
- 每格最多放置一個實體包裝。
- 每架最多十個包裝。
- 全藥局最多七十個包裝。
- 允許同種藥品重複擺放。
- 不限制每架最低藥品種類，允許完全空架。
- 不設置實體格位隔板，採用視覺框線。
- 空格平時為淡色框線，選藥後加強合法放置格位。

刪除整座藥架需要二次確認，並清除該架的擺放紀錄，但不得刪除個人藥品目錄中的品項。

單格藥品替換與丟棄均不需要二次確認。

### 6.7 藥品點擊資訊

未點選架上藥品時，不額外顯示浮動藥名標籤。

點擊後顯示：

- 英文學名。
- 商品名。
- 劑量。
- 劑型。

商品名未填寫時可以隱藏該欄。

其他選填資訊仍保留在個人藥品管理頁，不額外加入藥架點擊資訊面板。

### 8.1 管理端

管理端使用獨立網址，例如：

`/admin/`

實際部署路徑須相容 GitHub Pages 的 Repository 子路徑。

管理頁不需要額外登入機制。

提供以下功能：

- 逐一新增管理端藥品。
- 編輯與管理教材草稿。
- 建立主題教材。
- 選擇主題包含的藥品。
- 預覽主題內容。
- 手動輸入主題代碼。
- 驗證教材及圖片。
- 匯出可供 GitHub 維護者發布的完整發布包。

管理端草稿可使用獨立 IndexedDB。

不得將 GitHub 寫入憑證、Personal Access Token、API 金鑰或其他秘密資訊寫入前端程式碼。

管理端無登入不代表具有公開寫入權限。

真正的教材發布必須透過具有 GitHub Repository 寫入權限的維護者完成。

### 8.2 主題代碼

維持 v22 的正式規格：

- 管理員自行輸入。
- 恰好六位 ASCII 英數字元。
- 至少包含一位英文字母及一位數字。
- 統一儲存為大寫。
- 使用者輸入時忽略大小寫。
- 排除 O、0、I、1。
- 永久有效，直到管理員手動停用。
- 可停用及重新啟用。
- 所有已發布代碼永久保留其占用狀態，不得分配給其他版本。
- 不提供隨機代碼生成機制。

原始輸入須先驗證合法字元，再進行大寫正規化。

應拒絕不合法的空白、標點符號及非 ASCII 字元。

### 8.3 版本與發布

每次修改已發布教材內容，均須建立新版本及新代碼。

舊版本內容不得直接覆蓋。
