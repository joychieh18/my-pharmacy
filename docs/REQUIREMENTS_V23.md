## 一、專案背景及任務目標

你是一位具有 React、TypeScript、Three.js、React Three Fiber、3D 場景建模、WebGL 效能最佳化及網頁互動介面開發經驗的資深程式設計師。

Repository：

https://github.com/joychieh18/my-pharmacy

正式遊戲：

https://joychieh18.github.io/my-pharmacy/

教材管理端：

https://joychieh18.github.io/my-pharmacy/admin/

互動式新手管理手冊：

https://joychieh18.github.io/my-pharmacy/ADMIN_GUIDE.html

經過實際試玩後，目前發現以下問題：

1. 每個藥架格位僅顯示一個藥品包裝，導致整座藥架看起來過於空曠。
2. 藥品模型偏小，包裝上的學名及劑量難以辨識。
3. 包裝貼圖解析度不足。
4. 上傳的圖片在藥品模型正面顯示面積過小，且容易出現大量留白。
5. 無圖片藥品皆使用白色包裝，整座藥架裝滿後缺乏色彩變化。
6. 獨立藥架的相機縮放及移動限制，使使用者難以近距離觀察藥品。

本次開發目標為：

- 模擬真實社區藥局整齊、充足的商品陳列。
- 提高藥品包裝的文字及圖片辨識度。
- 建立具有一致美術風格及豐富色彩的通用藥品包裝。
- 改善圖片上傳及裁切體驗。
- 提高獨立藥架近距離觀看的便利性。
- 在大量模型、高解析度貼圖的情況下維持合理的執行效能。

本次版本命名為：

**My Pharmacy v23 — Full Shelf Display & Enhanced Medication Packaging**

本次暫不處理 Cloudflare Pages、網址更換、GitHub 帳號移轉或部署架構調整。

請直接進行實際程式修改、測試及 Git 提交，不需要再次提供開發前的規劃報告。

## 四、藥架整格補貨及多包裝陳列

### 4.1 核心概念

將原本的「每格一個包裝」修改為「每格同一品項的完整商品陳列」。

一個格位仍然只對應一種藥品品項。

使用者上架一次後，系統自動生成多個相同的包裝模型，模擬真實社區藥局將同一品項整齊補滿架位的效果。

同一格位內所有包裝必須具有完全相同的：

- 英文學名。
- 劑量。
- 劑型。
- 包裝模板。
- 包裝尺寸。
- 包裝配色。
- 包裝圖片。
- 材質及文字資訊。

不得自動混入其他品項。

系統生成的包裝數量純粹屬於視覺呈現，不代表實際庫存數量。

### 4.2 實際格位淨空計算

請先檢查既有藥架及格位設定：

- 藥架總寬。
- 藥架總高。
- 藥架總深度。
- 各層層板位置。
- 層板厚度。
- 金屬支柱位置及尺寸。
- RX 藥架背板位置及厚度。
- 格位中心座標。
- 兩格層及三格層的各格寬度。

維持既有藥架基本規格：

- 寬 120 cm。
- 高 180 cm。
- 深 40 cm。
- 四層。
- 每層格位數依序維持 2、3、3、2。
- 每座藥架共十格。
- 全藥局最多七座藥架、七十格。

注意：各格位實際可用深度及寬度應扣除必要結構及安全間距，不得直接使用整座藥架外部尺寸進行計算。

### 4.3 自動排列規則

採用以下排列方式：

**橫向及縱深補滿，單層直立排列。**

具體要求：

1. 依格位實際淨寬及包裝寬度計算橫向可排列數量。
2. 依格位實際淨深及包裝深度計算向後排列數量。
3. 所有包裝直立擺放。
4. 所有包裝正面朝向藥架正面。
5. 同一排包裝在水平方向整體置中。
6. 第一排優先靠近藥架前緣，但須保留合理安全距離。
7. 後續包裝朝藥架內部依序排列。
8. 包裝間保留合理的小間距。
9. 建議初始包裝間隔為 1 cm，再依實際渲染成果合理調整。
10. 不進行垂直堆疊。
11. 不改變包裝模型尺寸以增加數量。
12. 不得與相鄰格位包裝重疊。
13. 不得穿過藥架支柱、背板或層板。
14. 不得超出格位邊界。
15. 不為了補滿而將包裝旋轉成側面朝前。

橫向及縱深排列數量應由共用演算法自動計算。

可以使用以下概念作為計算基礎：

橫向數量 = floor((可用寬度 + 間距) / (包裝寬度 + 間距))

縱深數量 = floor((可用深度 + 間距) / (包裝深度 + 間距))

實際實作須依模型邊界、支柱位置、背板位置及安全距離修正。

不得將上述計算公式直接視為已驗證的最終排列結果。

### 4.4 不同格位及包裝類型

必須分別測試：

- 兩格層的藥盒。
- 三格層的藥盒。
- 兩格層的藥瓶。
- 三格層的藥瓶。
- 兩格層的藥袋。
- 三格層的藥袋。
- OTC 藥架。
- RX 藥架。

若不同結構造成格位淨深不同，應依實際空間分別計算。

不得將全部包裝數量寫死為固定值。

### 4.5 資料模型

保留每格只引用一個藥品品項的資料設計。

例如某格位引用 Metformin 500 mg：

即使該格位渲染多個相同藥盒，資料層仍只保留一筆格位與藥品的關聯。

禁止為視覺陳列而：

- 複製藥品目錄資料。
- 建立額外的藥品 ID。
- 建立多筆相同格位的擺放資料。
- 新增庫存管理功能。
- 新增補貨數量欄位。
- 新增個別包裝數量管理。
- 修改既有藥品重複判斷規則。

全藥局仍然最多七十個已占用格位。

實際渲染的包裝模型數量可超過七十個。

## 五、藥品上架及操作行為

### 5.1 上架

使用者選擇藥品後，點擊合法空格。

系統自動生成該品項的完整陳列。

不需要逐個擺放模型，也不需要輸入補貨數量。

### 5.2 替換

使用者替換格位藥品時：

- 移除原有完整陳列。
- 保留格位位置。
- 依新藥品的包裝模板及尺寸重新計算排列。
- 顯示新藥品的完整陳列。

不得殘留舊包裝模型或舊材質。

### 5.3 丟棄

丟棄格位中的藥品時，一次清除該格位全部視覺包裝。

格位恢復空白，並保留原有合法格位提示功能。

### 5.4 點擊

點擊同一格位中的任一實體包裝，均對應該格位的同一藥品。

不得因為模型數量增加而使使用者必須精確點擊某個特定包裝。

應維持原有藥品資訊及編輯操作。

### 5.5 其他既有操作

保留：

- 藥品目錄編輯。
- 刪除藥品及級聯清除其所有格位。
- 藥架刪除。
- 藥架新增。
- 藥架命名。
- 重新開始。
- 總覽及獨立藥架切換。
- 空格高亮。
- OTC／RX 分類提醒。
- 未分類藥品提醒。

分類提醒每次上架或替換只觸發一次，不得因為生成多個包裝而重複觸發。

## 六、圖片上傳容量及解析度改善

### 6.1 上傳容量

將圖片上傳容量由原本 2 MB 提高至 5 MB。

統一使用：

`5,000,000 bytes`

應同步修改：

- 學生端圖片上傳驗證。
- 教師管理端圖片上傳驗證。
- 教材發布包圖片驗證。
- 教材載入驗證。
- GitHub Actions 教材驗證腳本。
- 教材 Schema 或相關驗證文件。
- 使用者介面提示。
- 錯誤訊息。
- 管理手冊。
- 自動化測試。

保留原有支援格式：

- PNG。
- JPG。
- JPEG。
- WebP。

仍須驗證實際圖片能夠正確解碼。

不得只修改介面顯示的容量上限，而未修改後端建置或教材驗證邏輯。

### 6.2 圖片最長邊

將圖片處理後的最長邊上限由 1024 px 提高至 2048 px。

要求：

1. 保留原始圖片長寬比例。
2. 超過 2048 px 的圖片等比例縮小。
3. 不得任意拉伸圖片。
4. 不得要求所有圖片強制變成正方形。
5. 不得將低解析度圖片放大後宣稱其原始畫質提升。
6. 保留既有圖片壓縮及格式轉換機制，並依實際品質合理最佳化。
7. 處理後圖片亦須符合正式教材圖片容量限制。
8. 避免重複轉碼造成不必要的畫質損失。

### 6.3 3D 貼圖解析度

將原有 512 px 標籤 Canvas 改善為最高最長邊 2048 px 的高品質貼圖。

Canvas 長寬比應依實際包裝表面比例決定。

自動生成的文字貼圖及使用者上傳的圖片貼圖，皆應支援高品質近距離顯示。

請適當使用：

- 正確的 sRGB 色彩空間。
- 適當的 mipmap。
- 合適的 minification 及 magnification filtering。
- Anisotropic filtering。
- 裝置支援範圍內的貼圖解析度。
- 共用 CanvasTexture 或其他有效的貼圖快取策略。

不得為每個實體包裝複製獨立的高解析度貼圖。

若低效能裝置無法負荷最高解析度，可使用適當的渲染品質調整，但應優先保留近距離辨識品質。

### 6.4 場景渲染清晰度

評估調整 Canvas device pixel ratio。

建議由目前的最高 1.5 提升至最高 2，並依裝置及效能需求動態限制。

不得為提高畫面清晰度而導致大量不必要的 GPU 負擔。

請記錄最終採用的 DPR、貼圖解析度及渲染品質策略。

## 七、藥盒及藥袋全正面貼圖

### 7.1 正面貼圖範圍

將藥盒及藥袋的上傳圖片改為可使用整個模型正面。

目前原始碼曾採用約 94% 寬度及 76% 高度的正面標籤範圍，請以最新程式實際設定為準進行改善。

新版應做到：

- 正面圖片接近完整覆蓋。
- 不保留刻意的大片白色邊框。
- 不將圖片限制在模型中央的小矩形區域。
- 不發生貼圖與模型表面之間明顯的浮空效果。
- 不發生 Z-fighting。
- 不將正面圖片延伸至包裝其他表面。
- 不任意拉伸圖片以填滿模型。

允許為了模型倒角、材質邊界或避免渲染瑕疵保留極小的技術性邊距。

### 7.2 上傳圖片的側面及背面

有上傳圖片的藥盒及藥袋：

- 正面使用上傳圖片及使用者設定的裁切結果。
- 側面維持白色。
- 背面維持白色。
- 頂部及底部維持白色。

不自動擷取圖片主色搭配其他表面。

不將圖片複製至所有表面。

不額外加入彩色裝飾覆蓋使用者上傳的圖片。

### 7.3 圖片與文字

若使用者已經上傳包裝圖片，以該圖片作為包裝正面的主要內容。

不額外強制疊加學名及劑量文字，以免遮蔽真實包裝圖片。

學名及劑量仍應透過既有藥品資訊介面正確顯示。

## 八、藥瓶曲面標籤

### 8.1 標籤貼合方式

將藥瓶原本的平面標籤修改為沿圓柱瓶身曲面貼合的標籤。

要求：

1. 標籤必須沿著瓶身曲率自然彎曲。
2. 不得使用明顯懸浮於圓柱前方的平面矩形。
3. 正面觀看時，主要文字及圖片應容易辨識。
4. 轉動相機觀看側面時，標籤應自然延伸至曲面。
5. 避免 UV 拉伸、鏡像、接縫或圖片重複造成的視覺瑕疵。
6. 標籤不得與瓶身發生穿模或 Z-fighting。
7. 維持正式藥瓶直徑及高度。

可以使用適當的曲面幾何、UV mapping 或其他 Three.js 材質技術。

### 8.2 有圖片的藥瓶

有上傳圖片的藥瓶：

- 以正面曲面標籤呈現上傳圖片。
- 標籤以正面為中心，沿瓶身合理範圍彎曲。
- 標籤以外的瓶身區域維持白色。
- 不要求圖片包覆整個 360 度瓶身。
- 不自動將圖片主色延伸至其他表面。
- 不新增不必要的品牌標誌。

標籤的覆蓋角度、高度及細部 UV 配置，交由開發者依實際觀看效果合理設計。

需提供正面及側面的實際渲染截圖。

### 8.3 無圖片的藥瓶

沿瓶身曲面顯示本次新版自動生成的彩色通用標籤。

與藥盒及藥袋維持一致的品牌美術語言。

## 九、圖片裁切及預覽介面

### 9.1 預設顯示模式

將新上傳圖片的預設顯示方式修改為：

**填滿裁切（Cover／Fill）**

圖片應優先完整覆蓋可用貼圖區域。

若原始圖片比例與模型表面比例不同，允許裁切，但不得任意變形。

保留兩種模式：

1. 填滿裁切。
2. 完整顯示（Contain）。

已存在的舊藥品，其明確儲存的裁切設定應完整保留，不得因為新版預設值改變而被強制重置。

### 9.2 直接拖曳

在圖片裁切介面中提供直接操作功能。

使用者可以：

- 使用滑鼠拖曳圖片。
- 使用觸控拖曳圖片。
- 調整水平及垂直位置。
- 放大圖片以裁切特定區域。
- 縮小至當前模式允許的最小比例。
- 重置裁切設定。

提供易於理解的操作提示。

若保留原本的滑桿作為輔助操作，拖曳與滑桿的狀態必須同步。

### 9.3 裁切框

2D 裁切框的長寬比例必須對應實際包裝模板的貼圖範圍。

不同包裝模板切換時，裁切框應正確更新。

藥瓶須依實際曲面標籤展開比例呈現合理的裁切預覽。

裁切時不得讓使用者誤以為某區域會顯示，實際卻被模型裁切掉。

### 9.4 即時預覽

圖片裁切介面須同時提供：

- 清晰的 2D 裁切結果預覽。
- 即時 3D 包裝預覽。

當使用者移動圖片、調整縮放比例或切換包裝模板時，預覽須正確更新。

不應要求先儲存藥品才能看到裁切結果。

應適度節流或合併貼圖更新，避免拖曳時頻繁建立高解析度 GPU 資源。

### 9.5 包裝模板切換

當使用者由藥盒切換至藥瓶或藥袋時：

- 正確更新模型尺寸。
- 正確更新裁切框比例。
- 正確更新 3D 預覽。
- 保留圖片原始資料。
- 依新表面比例合理套用裁切資訊。
- 若裁切可能造成大量內容遺失，允許使用者重新調整。

不得要求重新上傳原始圖片才能切換包裝模板。

### 9.6 共用介面

新版圖片上傳及裁切介面應同時適用於：

- 學生新增藥品。
- 學生編輯藥品。
- 教師新增教材藥品。
- 教師編輯教材藥品。

優先共用元件及資料處理邏輯，避免兩端功能不一致。

## 十、無圖片藥品的自動彩色通用包裝

### 10.1 美術方向

將無圖片藥品由原本純白色、中央文字的簡單模型，改善為：

**白色基底搭配彩色區塊的簡潔現代藥品包裝。**

整體應具有：

- 社區藥局商品陳列感。
- 專業藥學教育風格。
- 清楚的文字層級。
- 明確的品項視覺區辨。
- 適度的色彩豐富度。
- 一致的原創美術設計。

保留原有藥局白色及醫療綠的整體室內設計。

新增色彩主要集中於藥品包裝，不需要重新設計房間或藥架。

### 10.2 包裝正面設計

建議採用：

- 白色主背景。
- 彩色頂部區塊或色帶。
- 清晰且足夠大的學名。
- 容易辨識的劑量文字。
- 適當的彩色底部區塊或簡潔幾何裝飾。
- 合理的留白。
- 高對比字體。

不得使用過度複雜的圖案妨礙文字辨識。

不需要模仿現有真實藥廠或品牌包裝。

不得加入未經確認的藥廠名稱、適應症、療效宣稱、認證標誌或虛構藥品資訊。

### 10.3 自動生成包裝文字

自動生成包裝的藥品文字只包含：

1. 英文學名。
2. 劑量。

維持原 v22 資訊規格。

不額外印製：

- 商品名。
- 藥理分類。
- 適應症。
- OTC／RX 分類。
- 劑型名稱。
- 虛構製造商名稱。

### 10.4 無圖片包裝的其他表面

無圖片藥盒及藥袋的側面、頂部或其他可見區域，可以合理使用與正面一致的彩色色帶或幾何設計。

無圖片藥瓶可使用相同主色的彩色曲面標籤。

須維持白色基底，不改為所有表面完全滿版純色。

此規則僅適用於無圖片包裝。

有上傳圖片的包裝其他表面仍維持白色。

## 十一、自動配色及手動配色

### 11.1 自動配色

對沒有上傳圖片的藥品，自動分配一組穩定的包裝主色。

應依藥品品項的穩定識別資訊進行計算，例如：

- 正規化英文學名。
- 正規化劑量。
- 固定劑型 ID。

不得每次開啟頁面或重新渲染時隨機選擇不同顏色。

同一個品項在不同格位、不同藥架、總覽及獨立藥架中，應使用相同配色。

若無手動指定配色，同一品項由相同自動配色規則生成一致結果。

### 11.2 配色原則

建立足夠豐富且具有一致風格的色票。

建議涵蓋：

- 藍色。
- 青色。
- 綠色。
- 紫色。
- 橘色。
- 珊瑚紅。
- 芥末黃。
- 深藍色。
- 灰藍色。
- 其他適合藥品包裝的色彩。

色彩須具備適當飽和度及文字對比。

避免大量過於相近、難以區辨的顏色。

配色僅供品項視覺區辨，不代表藥理分類、藥物安全性或真實包裝標準。

不得藉由顏色暗示處方藥或非處方藥分類。

### 11.3 手動配色功能

在學生端及教師管理端藥品表單中，新增選填的包裝配色設定。

提供：

- 自動配色（預設）。
- 多個預設色票供使用者選擇。
- 即時包裝預覽。
- 恢復自動配色。

不將配色設定列為新增藥品的必填欄位。

不要求使用者輸入 HEX 或 RGB 色碼。

有上傳圖片時，圖片優先決定正面外觀，其餘表面維持白色。

手動配色可保留於藥品資料中，但在有圖片時不應覆蓋上傳圖片，亦不應改變白色側面及背面。

移除圖片後，可恢復使用該品項原有的手動配色或自動配色。

### 11.4 修改配色後的行為

使用者編輯既有藥品的包裝配色時：

- 更新所有引用該藥品的格位。
- 同步更新同格全部實體包裝。
- 同步更新藥局總覽。
- 同步更新獨立藥架。
- 保留藥品 ID。
- 保留原有擺放紀錄。
- 不建立重複藥品。

## 十二、藥品文字辨識度

### 12.1 文字排版

自動生成標籤中，英文學名與劑量必須清楚且具有視覺層級。

要求：

1. 英文學名採用清晰、適合包裝印刷的字體。
2. 使用適當粗體。
3. 文字與背景維持高對比。
4. 優先使用完整可用的正面文字空間。
5. 依名稱長度動態調整字級。
6. 英文學名過長時，優先進行合理的單字換行。
7. 必要時才進行字元層級換行。
8. 不讓文字超出包裝範圍。
9. 不因文字過長而任意省略學名。
10. 劑量須保持完整。
11. 避免學名與劑量重疊。
12. 不要求使用者自行設計標籤。

### 12.2 貼圖清晰度

文字生成的 Canvas 尺寸應與最高 2048 px 貼圖設定相容。

應根據實際 Canvas 尺寸重新計算文字大小、留白、行距及排版。

不得只將 Canvas 尺寸由 512 改為 2048，卻沿用原本固定的文字像素大小，導致文字在包裝上的相對比例反而縮小。

### 12.3 真實辨識限制

不要求藥局總覽中每一個藥盒的全部文字均可清楚閱讀。

總覽主要用途仍為：

- 藥局空間辨識。
- 藥架位置辨識。
- 商品陳列效果。
- OTC／RX 分區辨識。

獨立藥架應透過更近距離縮放及平移，提供較好的藥品文字辨識能力。

## 十三、獨立藥架相機及觀看操作

### 13.1 更近距離縮放

調整獨立藥架的相機控制，使使用者能夠比 v22 更靠近藥品包裝。

要求：

- 能觀看整座藥架。
- 能放大某一層。
- 能近距離觀察某個格位及其中包裝。
- 滾輪及觸控縮放應自然操作。
- 避免縮放時穿過包裝或藥架結構。
- 避免物件因相機裁切平面不合理而消失。
- 保留合理的最大縮放距離。

實際最小及最大相機距離，交由開發者依新包裝尺寸、畫面大小及可辨識性測試後決定。

### 13.2 平移

在獨立藥架視角中加入平移功能。

使用者放大後，可以移動觀看位置至：

- 藥架上層。
- 藥架下層。
- 左側格位。
- 右側格位。
- 不同包裝位置。

平移範圍應受到合理限制，避免藥架完全移出畫面後無法尋回。

桌面及行動裝置均應有容易理解的操作方式。

建議保留或提供簡短的操作提示。

### 13.3 相機重置

保留既有相機重置功能。

重置後須：

- 恢復完整藥架正面視角。
- 恢復合理預設縮放距離。
- 恢復預設觀看目標。
- 不改變藥架內的任何藥品。

### 13.4 總覽相機

本次主要修改獨立藥架的近距離觀看能力。

保留原 v22 藥局總覽的主要觀看方式及場景配置。

如為配合放大後模型而需進行微幅相機調整，應記錄原因，不得擅自改變整體觀看方向及操作模式。

## 十六、渲染效能最佳化

本次將同時增加：

- 每格實體包裝數量。
- 貼圖最高解析度。
- 圖片容量。
- 近距離觀看需求。

因此，效能最佳化為本次正式開發需求，不是可省略的後續功能。

### 16.1 模型實例化

優先評估使用：

- Three.js InstancedMesh。
- React Three Fiber 相容的實例化機制。
- 共用 Geometry。
- 共用 Material。
- 共用 Texture。

同一格位多個相同包裝，優先以實例化或其他有效方式減少 draw calls。

不得直接為每個實體包裝複製整個 React 包裝元件，並各自建立 CanvasTexture。

應依實際模型組成，對包裝本體及正面標籤採用適當的共用和實例化策略。

### 16.2 貼圖快取

同一藥品在多個格位及藥架中的包裝，應盡可能共用相同貼圖。

只有在以下內容實際改變時，才需要重新生成相應貼圖：

- 英文學名。
- 劑量。
- 包裝模板。
- 自動或手動配色。
- 上傳圖片。
- 裁切設定。
- 必要的渲染品質設定。

切換視角或相機移動，不應無故重新生成全部藥品貼圖。

### 16.3 資源釋放

下列情況應正確釋放不再使用的 GPU 或瀏覽器資源：

- 編輯藥品。
- 更換圖片。
- 替換格位藥品。
- 清空格位。
- 刪除藥品。
- 刪除藥架。
- 重新開始。
- 元件卸載。
- 切換主要介面。

注意共用貼圖資源的使用者數量。

不得在其他格位仍使用某張貼圖時提前釋放。

避免：

- GPU memory leak。
- CanvasTexture leak。
- 未釋放的 Object URL。
- 大量重複 Geometry。
- 大量重複 Material。
- 不必要的重新渲染。

### 16.4 細節層級

若需要，可依觀看距離使用合理的 Level of Detail 或其他渲染最佳化。

例如：

- 總覽使用適合遠距離觀看的渲染品質。
- 獨立藥架使用較高細節。
- 近距離使用高解析度貼圖。
- 對完全被遮蔽的模型進行合理裁切。

但不得因效能最佳化而使藥架重新看起來空曠。

不得破壞整格補貨的核心視覺要求。

### 16.5 滿載測試

必須測試全部七座藥架、七十個格位均已上架的情境。

至少包含：

A. 全部格位使用藥盒。

B. 全部格位使用藥袋。

C. 混合藥盒、藥瓶及藥袋。

D. 多個格位使用相同藥品。

E. 多個格位使用不同藥品及不同圖片。

F. 多個高解析度圖片品項同時存在。

在可用環境中記錄：

- 測試裝置及瀏覽器。
- 實際渲染模型數量。
- Draw calls。
- 可取得的 Geometry 及 Texture 資源統計。
- 可取得的 FPS 或 frame time。
- 初次載入時間。
- 旋轉、縮放、平移及視角切換體驗。
- 是否出現 WebGL context loss。
- 已知限制。

應說明測量方式及測試環境。

不得虛構實體 GPU 記憶體使用量、FPS 或行動裝置測試結果。

若 headless Chromium 使用軟體渲染，請明確標記其效能結果不能直接代表真實裝置。

不得加入：

- 編輯藥品。

- 修改格位。
- 匯入回遊戲。
- 遊戲備份或恢復。
